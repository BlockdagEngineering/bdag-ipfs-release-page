BlockDAG 2.0.0-community-rescue-rc.62

A software-only installer correction for mainnet chain ID 1404. RC62 makes the public mining profile installable with the complete signed payload inventory, keeps the local-peer controller attached to the authenticated active release, and makes dual-runtime rollback deterministic on Bash 5.2.

Installer correction published. Both architecture packages, the signed release records, and their immutable IPFS identities passed the RC62 publication gates.

What RC62 fixes

RC62 carries the two reproducible RC58 installer corrections and fixes the Bash 5.2 dual repair-lock rollback failure found by RC60/RC61 protected preflight, while preserving signed-lock, rollback, data-continuity, and reward-accounting behavior.

Complete signed inventoryThe mining-profile installer now loads the signed digest for ops/local_chain_attestation.py before privileged staging. Loader and staged inventories must remain exactly equal.
Stable local-peer servicebdag-local-peers.service runs a signed stable wrapper and reads the installer-owned active project-root record instead of embedding a retired release path.
Authenticated retryAn interrupted upgrade may recover its prior runtime only after both release roots authenticate and their Compose, node-data, release-lock, chain, fork, and checkpoint identities match.
Tampering still fails closedA changed lock, mismatched Compose identity, unsafe path, symlink, or arbitrary custom bdag-* controller is rejected before service mutation.
Immutable historyRC58 and RC59 remain unchanged. RC60 and RC61 failed protected preflight and are not published. Sequence 62 contains the Bash 5.2-safe correction and requires complete signed packages for both architectures; historical signed locks keep their original validity.
Exact reward precision retained23,983,626,033 atomic units remain exactly 239.83626033 BDAG; the RC58 arbitrary-precision accounting correction is preserved.
Data remains independentRC62 publishes no dataset. Existing compatible chain data and Postgres volumes are preserved, or a node synchronizes normally.
Public defaultsFresh installation defaults to sync-only/no-miner. Mining, public RPC, software-only upgrade, and data restore remain explicit independent choices.
Consensus unchangedConsensus subsidy, block-header validation, cumulative-work selection, miner eligibility, chain ID, and P2P protocol behavior are unchanged.

Verify before installing

A successful download is not enough. Verify the exact bytes and the signed trust records.

Software

  1. Match the package SHA-256 to the release manifest.
  2. Verify the release authorization signature with the published release key.
  3. Confirm the release key fingerprint and signed release sequence.
  4. Run the packaged installer, which verifies its signed release lock before activation.

Existing chain data

  1. RC62 supplies no portable or full-archive dataset.
  2. Preserve compatible native, EVM, and pool accounting data before upgrading.
  3. Use Keep / sync; never substitute an earlier release's dataset as an RC62 artifact.
  4. Never merge database or freezer directories from different histories by hand.
curl -4 --http1.1 -fL --retry 12 --retry-all-errors -C - \
  "https://GATEWAY.example/ipfs/CID_FROM_RELEASE_MANIFEST" \
  -o "ARTIFACT.part"
printf '%s  %s\n' "SHA256_FROM_RELEASE_MANIFEST" "ARTIFACT.part" | sha256sum -c -

When an IPFS gateway times out

A gateway timeout does not change the CID or the file. Resume through another gateway and verify the final hash. If the IPFS page itself is unavailable, use the stable web copy.

1. Keep the partial fileDo not delete .part. The documented command resumes it with -C -.
2. Change the gatewayTry each gateway listed in the release manifest while keeping the same CID and output filename.
3. Force the stable transportKeep both -4 and --http1.1 on every large download.
4. Verify after assemblyTrust only the published SHA-256 and signature records, regardless of which gateway returned the bytes.
